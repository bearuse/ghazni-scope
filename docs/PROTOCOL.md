# Ghazni Scope 스트림 형식 (버전 3)

타깃(RTOS)이 PC 도구로 보내는 바이트의 형식입니다. Ghazni 커널과 FreeRTOS 기록기가 똑같은 형식을 보내고, 도구(`ghazni-scope`, `ghazni_scope/`)는 둘을 구분하지 않고 읽습니다. **다른 RTOS에 Scope를 붙이려면 이 형식으로 보내기만 하면 됩니다.** C 정의는 `include/scope_proto.h`, 압축·포장 코드는 `include/scope_encode.h`(헤더만, libc 없이 동작)에 있으니 그대로 가져다 쓰세요.

모든 정수는 리틀 엔디언입니다.

## 1. 바이트 흐름: 콘솔 글 사이에 낀 프레임

```
... 콘솔 글 ... 0x01 [COBS로 포장한 프레임] 0x00 ... 콘솔 글 ... 0x01 [프레임] 0x00 ...
```

- 프레임은 `0x01`(시작)로 시작해 `0x00`(끝)으로 끝납니다.
- 프레임 내용은 [COBS](https://en.wikipedia.org/wiki/Consistent_Overhead_Byte_Stuffing)로 포장해 `0x00`이 없게 만듭니다. 그래서 `0x00`을 보면 언제나 프레임의 끝입니다. COBS는 254바이트마다 1바이트만 늘립니다.
- 그 밖의 바이트는 콘솔 글로 취급되어 도구의 Console 화면과 터미널에 나옵니다. 콘솔 글에는 `0x00`과 `0x01`이 없어야 합니다(보통 글자에는 없습니다).
- 그래서 UART 하나를 printf 콘솔과 Scope가 같이 쓸 수 있습니다. 단, 프레임 하나는 중간에 다른 글이 끼어들지 않게 한 번에 보내야 합니다.
- 중간에 바이트를 잃으면(UART 잡음) 그 프레임만 버려지고 다음 `0x01`부터 다시 맞춰집니다.

`scope_wire(frame, n, out)`이 `0x01 + COBS + 0x00`을 한 번에 만듭니다.

UDP처럼 데이터그램으로 보낼 때도 같은 포장을 쓰고, 데이터그램 하나에 프레임 여러 개를 넣어도 됩니다(프레임이 데이터그램 경계에 걸치면 안 됨).

## 2. 프레임 종류

프레임의 첫 바이트가 종류입니다.

| 종류 | 언제 보내나 | 내용 |
|---|---|---|
| `'H'` hello | 처음에, 태스크가 생기거나 바뀔 때, 그리고 1초마다(반복 표시) | 버전, CPU 수, 시각 주파수, 태스크 목록 |
| `'O'` objects | 객체·인터럽트 이름이 바뀔 때, 1초마다 | 객체(큐, mutex ...)와 인터럽트의 이름·종류 |
| `'D'` events | 10 ms마다 (모인 이벤트가 있으면) | 압축한 이벤트 여러 개 |
| `'S'` stats | 100 ms마다 | 태스크별 CPU 시간, 상태, 우선순위, 스택 |
| `'X'` stopped | 스트림을 끌 때 (선택) | 없음 |

### 2.1 'H' hello

| 위치 | 크기 | 내용 |
|---|---|---|
| 0 | 1 | `'H'` |
| 1 | 1 | 버전 = 3 |
| 2 | 1 | CPU 수 |
| 3 | 1 | 태스크 수 n |
| 4 | 1 | 1 = 반복(이미 보낸 것을 다시 보냄), 0 = 새 스트림 |
| 5 | 1 | 어느 OS인가: 0 Ghazni, 1 FreeRTOS (화면 제목, 문구에 씀) |
| 6 | 2 | 0 |
| 8 | 8 | 시각 주파수(Hz): 이벤트 시각 1 = 1/Hz 초 |
| 16 | 20 × n | 태스크마다: id(1), 기본 우선순위(1), 0, 0, 이름(16, 0으로 채움) |

- **반복 표시가 0인 hello를 받으면 도구는 기록을 모두 지우고 새로 시작합니다.** 타깃이 재부팅됐을 때 쓰입니다. 태스크가 늘었을 뿐이면 반복 표시 1로 보내세요(기록이 유지되고 이름만 갱신됨).
- hello를 받기 전의 이벤트는 해석할 수 없어 버려집니다. 연결 도중에 도구를 켜도 1초 안에 반복 hello가 오므로 화면이 시작됩니다.
- 태스크 id는 0~252. **0xFF는 그 CPU의 idle**(아무것도 안 함), **0xFE는 "없음/모름"**(예: 스케줄러 시작 전 힙 할당) 입니다. idle 태스크는 목록에 넣지 마세요.

### 2.2 'O' objects

| 위치 | 크기 | 내용 |
|---|---|---|
| 0 | 1 | `'O'` |
| 1 | 1 | endpoint 수 e (Ghazni의 IPC 채널; 다른 RTOS는 0) |
| 2 | 1 | 객체 수 m |
| 3 | 1 | 인터럽트 수 k |
| 4 | 16 × (e + m) | 이름: endpoint 먼저, 그다음 객체 |
| … | 16 × k | 인터럽트마다: 번호(u16) + 이름(14) |
| … | m | 객체마다 종류 1바이트 |

객체 종류:

| 값 | 종류 | signal 이벤트의 뜻 | take 이벤트의 뜻 |
|---|---|---|---|
| 0 | event (비트, Ghazni notification, 태스크 알림) | 비트를 보냄 (arg = 비트) | |
| 1 | mutex | 풂 | 잡음 |
| 2 | semaphore | 줌 (arg = 준 뒤 개수) | 가져감 (arg = 남은 개수) |
| 3 | queue | 보냄 (arg = 보낸 뒤 쌓인 수) | 받음 (arg = 남은 수) |
| 4 | event group | 비트 설정 (arg = 비트) | 기다리던 비트를 받음 |

객체 번호(이벤트의 b, 막힘 정보의 객체 번호)는 이 목록에서의 순서(0부터)입니다.

### 2.3 'D' events

| 위치 | 크기 | 내용 |
|---|---|---|
| 0 | 1 | `'D'` |
| 1 | 8 | 첫 이벤트의 일련번호 (이벤트마다 1씩 늘어남) |
| 9 | 2 | 이벤트 수 n |
| 11 | 1 | 0 |
| 12 | 4 | 이 프레임 앞에서 잃은 이벤트 수 (링이 넘쳐서) |
| 16 | 8 | 기준 시각 |
| 24 | … | 압축한 이벤트 n개 |

이벤트 하나는 이렇게 압축됩니다.

| 순서 | 형식 | 내용 |
|---|---|---|
| 1 | zigzag varint | 시각 − 앞 이벤트의 시각 (첫 이벤트는 기준 시각과의 차). 음수도 됨(CPU마다 시각이 조금 다를 때) |
| 2 | u8 | 종류(아래 4비트) \| CPU 번호 << 4. 종류가 16 이상이면 아래 4비트를 0으로 두고 다음 바이트에 종류 |
| 3 | u8 | a (대개 태스크 id) |
| 4 | u8 | b — `scope_has_b(종류)`일 때만 |
| 5 | varint | arg — `scope_has_arg(종류)`일 때만 |

varint는 7비트씩, 아래부터, 이어지면 최상위 비트 1(LEB128). zigzag는 0, −1, 1, −2 … 를 0, 1, 2, 3 …으로 바꾸는 것입니다. 대부분의 이벤트가 3~5바이트가 됩니다.

도구는 일련번호가 건너뛰면(프레임을 잃으면) "틈"으로, 잃은 수가 0이 아니면 "유실"로 화면 위쪽에 표시합니다.

`scope_frame_events(buf, 일련번호, 이벤트 배열, n, 잃은 수)`가 이 프레임 전체를 만듭니다. 이벤트 배열은 `struct scope_ev`(16바이트: 시각 u64, 종류, CPU, a, b, arg u32)입니다.

### 2.4 이벤트 종류

| 값 | 이름 | a | b | arg |
|---|---|---|---|---|
| 1 | SWITCH | 나가는 태스크 | 들어오는 태스크 | 나가는 태스크의 상태 \| 막힌 대상 종류 << 8 \| 대상 번호 << 16 (아래) |
| 2 | WAKE | 준비된 태스크 | | |
| 3 | IRQ | 끼어든 시점의 태스크 | | 인터럽트 번호 |
| 4 | TIMEOUT | 기다리다 시간이 다 된 태스크 | | |
| 5 | THROTTLE | CPU 예산을 다 쓴 태스크 | 대신 도는 태스크 | |
| 6 | TIMER | 태스크 | | 비트 |
| 7 | FAULT | 폴트 난 태스크 | | |
| 8 | CALL | 클라이언트 | 받은 서버 (0xFE = 대기열) | endpoint \| label << 8 (Ghazni IPC) |
| 9 | SEND | 〃 | 〃 | 〃 (답 필요 없음) |
| 10 | RECV | 서버 | 보낸 태스크 | endpoint |
| 11 | REPLY | 서버 | 클라이언트 | label |
| 12 | SIGNAL | 보낸/준 태스크 | 객체 번호 | 비트, 개수, 쌓인 수 (2.2 표) |
| 13 | USER | 태스크 | 채널 | 값 |
| 14 | USTR | 태스크 | 채널 \| 0x80(첫 조각) \| 0x40(상태 이름) | 글 4바이트 (0이 나오면 끝) |
| 15 | HEAP | 태스크 | 0 할당 / 1 해제 | 크기; 이어서 b \| 0x80, arg = 주소 아래 32비트 |
| 16 | IRQ_END | 끼어든 시점의 태스크 | | 인터럽트 번호 |
| 17 | PRIO | 태스크 | 새 실제 우선순위 | 이전 우선순위 |
| 18 | TAKE | 가져간 태스크 | 객체 번호 | 남은 개수·수 |

SWITCH의 arg, 나가는 태스크의 **상태**(아래 8비트):

| 값 | 상태 | 뜻 |
|---|---|---|
| 1 | running | (쓰지 않음) |
| 2 | ready | 선점당함: 막히지 않았는데 CPU를 뺏김 |
| 3 | send | 보내려다 막힘 (큐가 가득) |
| 4 | recv | 받으려다 막힘 (큐가 빔, 세마포어 0, mutex 잡힘) |
| 5 | reply | 서버의 답을 기다림 |
| 6 | wait | 비트·알림을 기다림 |
| 7 | sleep | 시간 지연 |
| 8 | faulted | |
| 9 | exited | 삭제됨 |
| 10 | stopped | 일시정지(suspend) |
| 11 | throttled | CPU 예산 소진 |

**막힌 대상 종류**(arg >> 8 & 0xFF): 0 없음, 1 endpoint, 2 객체('O'의 객체 번호), 3 태스크(답을 기다리는 서버). 대상 번호는 arg >> 16.

상태 3~10은 "스스로 멈춤"이라 도구가 여기서 인스턴스(한 번 깨어나 일하고 멈출 때까지)를 끊습니다. 화면의 `recv samples`, `lock bus_lock`(대상이 mutex면 recv를 lock으로 씀), `take isr_sem`, `wait flags`, `sleep`이 이 정보로 그려집니다.

### 2.5 'S' stats

| 위치 | 크기 | 내용 |
|---|---|---|
| 0 | 1 | `'S'` |
| 1 | 8 | 가동 시간(µs) |
| 9 | 1 | 태스크 수 n |
| 10 | 1 | 항목 크기 (32) |
| 11 | 1 | 0 |
| 12 | 4 | Scope 스트림을 보내는 데 쓴 시간(µs, 누적, 넘치면 돌아감) |
| 16 | 32 × n | `struct scope_task`: id, 상태, 실제 우선순위, 기본 우선순위, throttle 수(u32), CPU 시간 µs(u64), 스택 사용(u32), 스택 크기(u32), 커널 시간 µs(u64) |

모르는 값은 0으로 두면 됩니다(화면에 `–` 또는 0). 항목 크기를 보내므로 나중에 항목이 커져도 옛 도구가 읽을 수 있습니다.

## 3. 다른 RTOS에 붙이기: 할 일 목록

FreeRTOS 기록기(`targets/freertos/scope_freertos.c`, 약 530줄)가 그대로 본보기입니다.

1. **이벤트 기록 함수**: 인터럽트를 막고 `struct scope_ev` 하나를 RAM 링에 넣음. 링이 차면 버리고 센다.
2. **RTOS 훅에 연결**: 문맥 전환(SWITCH, 나가는 태스크가 왜 멈췄는지 함께), 준비됨(WAKE), 큐·세마포어·mutex 주기·가져가기(SIGNAL, TAKE), 우선순위 상속(PRIO). 대부분의 RTOS에 trace 훅이 있습니다(Zephyr의 tracing API, ThreadX의 TX_EVENT_TRACE, RT-Thread의 hook, embOS의 SystemView API 등).
3. **태스크·객체 번호**: RTOS의 TCB·객체 포인터를 0부터의 작은 번호로 바꾸는 표.
4. **보내는 태스크**: 주기적으로 링을 비워 `scope_frame_events` + `scope_wire`로 보내고, 'H'(1초마다 반복)와 'O', 'S'를 보냄.
5. 시험: `ghazni-scope --exec ... --check 5`가 요약을 출력하고, `SCOPE_JSON=파일`을 주면 도구가 본 것을 JSON으로 남깁니다. `tests/run_freertos.py`가 그것으로 확인하는 방법을 보여 줍니다.

hello의 OS 바이트에 새 값을 쓰려면 `ghazni_scope/protocol.py`의 `OS_NAME`에 이름을 더하세요(없으면 "os 2"처럼 나옵니다).

## 4. 버전

| 버전 | 바뀐 것 |
|---|---|
| 1 | 'C' 프레임 (이벤트 7가지) |
| 2 | 'D' 프레임(16가지 이벤트, b·arg를 종류에 따라 생략), 'O' 프레임 |
| 3 | 16 이상 종류(IRQ_END, PRIO, TAKE), 'O'에 인터럽트 이름·객체 종류, 'S' 항목 32바이트, hello의 OS 바이트 |

도구는 v1·v2 스트림도 읽습니다.
